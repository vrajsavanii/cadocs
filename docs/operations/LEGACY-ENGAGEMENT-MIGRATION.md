# Legacy Engagement Migration

**Status:** applied automatically at first boot (migration 4, `lib/db.ts`). This
describes what the migration actually does, how to read its report, and how to recover.

## Scope

Migration 4 — *"recurring-engagement-engine: period model, due-date rules, append-only
status history, generation runs"* — moves pre-Prompt-5 `compliance` rows onto the new
period model **in place**. It is additive:

- `ensureColumn` adds 18 columns to `compliance` and 2 to `client_services` (idempotent).
- `CREATE TABLE IF NOT EXISTS` for `due_date_rules`, `compliance_status_history`,
  `engagement_generation_runs`.
- New indexes (`internal_target_date`, `statutory_due_date`, `(service_id, period)`).
- No `DROP TABLE`, no id changes, no deletes. Invoices, payments, documents, UDIN,
  messages and audit rows are not touched.

## Backfill rules (what happens to an existing engagement)

| Input | Result |
|---|---|
| `period` free text + service frequency | `period_type` from the service's frequency; `period_start`/`period_end` parsed by `legacyPeriod` (month/quarter/H1-H2/AY/FY patterns) |
| unparsable period text | empty bounds, counted in `ambiguous_periods` — **nothing is invented** |
| old `due_date` | copied to `internal_target_date`; `due_date_source = "Legacy due date migrated as an unverified internal target"` |
| statutory columns | `statutory_due_date = NULL`, `due_date_verified = 0`, `statutory_rule_status = 'unverified'` — **no legacy row is ever labelled legally verified** |
| `due_rule_id` / `due_rule_version` | pointed at the seeded unverified v1 rule when the service is in the catalogue |
| `fy` / `assessment_year` | FY preserved; AY derived only for `service_code = 'itr'` |
| provenance | `generation_source = 'migration'`, `generated_at` backfilled |
| filing | `filing_reference ← ack_number`, `filing_recorded_at ← filed_date`, `filing_confirmed_by_integration = 0` |
| history | one baseline `HIST-M4-<id>` row per engagement (`actor = 'migration'`, reason recorded) |

Duplicate business keys in legacy data (same client/service/period/registration label)
are counted, not silently merged.

## The report

Stored in `settings` under the key **`engagement_migration_report_v1`**:

```json
{ "at": "...", "scanned": 123, "period_backfilled": 120, "ambiguous_periods": 3,
  "missing_service_code": 0, "duplicate_labels": 0 }
```

Read it with:

```sql
SELECT value FROM settings WHERE key = 'engagement_migration_report_v1';
```

Interpretation:

- `ambiguous_periods > 0` → those engagements have empty `period_start`/`period_end`;
  review them in `/compliance` and correct the period manually (a run with
  `period` set correctly will then be recognised as existing, not duplicated).
- `missing_service_code > 0` → rows created before the service catalogue; they will
  never be regenerated by the engine (the uniqueness index is partial on
  `service_code`), which is intentional: history stays untouched.
- `duplicate_labels > 0` → legacy rows sharing a business identity; the uniqueness
  index only constrains new writes, so these remain as-is for authorised review.

The Prompt 4 client migration has its own report under `client_migration_report_v1`.

## Verification steps (run after upgrade)

1. `npm run typecheck` and `npm test` — all suites pass (see
   [../testing/RECURRING-ENGAGEMENT-TEST-PLAN.md](../testing/RECURRING-ENGAGEMENT-TEST-PLAN.md)).
2. Confirm counts are unchanged: `SELECT COUNT(*) FROM compliance` before and after
   the upgrade must match.
3. Spot-check one previously filed engagement: `filed_date`, `ack_number` and its
   `documents`/`invoices` links are intact, `statutory_due_date` is NULL and
   `statutory_rule_status = 'unverified'`.
4. Read the report key and triage `ambiguous_periods` / `duplicate_labels`.
5. `GET /api/engagements/runs` after the first cron shows the baseline run.

## Rollback / forward recovery

- Migration 4 is recorded in `schema_migrations`; it does not re-run.
- Because the change is additive and id-referential, "rollback" of a failed deploy
  means restoring the pre-upgrade database snapshot (see
  [BACKUP-AND-RECOVERY.md](BACKUP-AND-RECOVERY.md)) and redeploying the previous
  build — the new columns are ignored by the old code.
- Never delete `compliance` rows to "clean up" duplicates: history, documents and
  invoices reference them, and the engine already refuses to regenerate existing
  periods.

## Production policy

No destructive migration is executed by hand. The migration runs inside the app's
startup transaction: if it fails, the database is left at the previous version and the
application reports the error — fix and restart. Take a backup first
(`npm run backup`).

## Known limitations

- Period parsing is best-effort for free-text legacy labels; unparsable rows are
  flagged, not guessed.
- The report lives in the database, not in a file or endpoint; operators read it with
  the SQL above (no UI surface in this phase).
